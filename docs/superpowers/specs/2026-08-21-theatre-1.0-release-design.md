# Theatre.js 1.0 发布设计(fork 路线)

日期:2026-08-21
状态:待用户审阅

## 背景

上游 theatre-js/theatre 的 main 分支停在 0.7.x(最后一个提交 2024-04-11,"1.0 开发转入私有仓库"的公告),npm 公开版本停留在 0.7.2。main 上留有 2023 Q4 的 1.0 方向性工作:monorepo 重构、新 `init()` API,以及一套做到一半的云协作代码(saaz 同步引擎、sync-server、Next.js 管理后台 app)。

关键现状:**Studio 的状态存储处于 Redux→Saaz 迁移中途,单人使用已退化**——

- `StudioStore.ts:71` 的 `|| true` 强制使用内存存储,项目编辑刷新后丢失
- `Studio.ts:694` 的 `serverUrl` 默认指向 `https://app.theatrejs.com`,浏览器端无条件创建 tRPC 后端
- `clearPersistentStorage`、`__dev_startHistoryFromScratch` 等方法 `throw 'Implement me?'`
- saaz 的 `SaazFront._init` 存在 `Not implemented` 分支

因此"不影响单人使用"不是隔离协作代码即可,单人路径本身必须修复完整。

## 目标与已确认决策

| 决策点 | 结论 |
|---|---|
| 1.0 中协作功能的状态 | **最小可用闭环**:离线本地持久化 + 可选自托管 sync-server,默认关闭,不含官方云服务;单人使用完全不受影响 |
| 分发方式 | **fork 新 npm scope** 发布,包名批量修改,README 说明与上游关系 |
| 向后兼容 | **state 兼容,API 可破**:0.7.x 的 project state JSON 必须能打开(带迁移);允许破坏性清理公共 API,附迁移指南 |
| 发布范围 | core / studio / r3f / react / dataverse / utils / browser-bundles / saaz / sync-server / theatric;**不含 app** |
| 投入节奏 | 业余节奏:任务拆小,每个任务 1–2 个会话可完成,里程碑不绑死日期 |
| 技术路线 | **路线 A:完成 Saaz 迁移**(附回退触发器,见下文) |

非目标:官方托管云服务、app 管理后台(留在仓库标 private,零投入)、studio UI 布局状态的迁移。

## 总体架构

Saaz 是唯一的状态引擎,单人与协作同构,区别只在后端实现:

```
单人模式(默认,纯离线):
  Studio UI → StudioStore → SaazFront ──进程内调用──→ SaazBack(本地后端)
                                 │                          │
                          FrontIDBAdapter            BackIDBAdapter(新建)
                                 └────────── IndexedDB ──────────┘

协作模式(仅当 init({serverUrl}) 时):
  Studio UI → StudioStore → SaazFront ──tRPC/WebSocket──→ sync-server(自托管)→ Postgres
```

核心架构决策:

1. **`serverUrl` 默认值从 `app.theatrejs.com` 改为 `undefined`**。不传 = 纯离线单人;传了才启用协作。可插拔点 `SaazBackInterface` 已预留,本地后端只是该接口的又一个实现。
2. **`BackStorageAdapter` 目前是空接口**(`saaz/src/types.ts:258`),后端持久化契约由本设计定义,表面极小:持久化 snapshot / clock / updates log 三项。
3. **P0 先做 fork 改名**。上游 main 已冻结,机械改名无 rebase 成本,先做确立仓库身份。

## 阶段划分

业余节奏,每个任务控制在 1–2 个会话。

### P0 基线与改名

- 跑通 jest / typecheck / compat-tests 基线,作为后续改动的对照组
- 选定新 npm scope 名称(P0 第一个任务),批量修改包名
- LICENSE/NOTICE 保留原归属(Apache-2.0);README 写明 fork 关系与原 1.0 公告的更替

出口标准:CI 绿,新 scope 全部包可构建。

### P1 单人可用性(关键路径)

- 完成 `FrontIDBAdapter`;补 `SaazFront._init` 的"磁盘快照 + 缓存后端状态共存"分支
- 设计 `BackStorageAdapter` 接口并实现 `BackIDBAdapter`;`SaazBack` 支持存储注入
- StudioStore 默认接本地后端(删 `|| true`);tRPC 后端仅在 `serverUrl` 存在时创建
- 补齐 `clearPersistentStorage`、`__dev_startHistoryFromScratch`(按 0.7.x 语义)
- 清理 `enhancedTrpcWsClient` 等处调试残留;验证 Auth 在无 serverUrl 时完全静默

出口标准:刷新不丢状态、零网络依赖可用、undo/redo 正常。

### P2 API 稳定化

- `__experimental_*` 逐个处置(转正 / 改名 / 删除),含 getKeyframes、forgetObject/forgetSheet、sequenceProp、rafDriver、persistent storage 系列、createContentOfSaveFileTyped 等
- 0.7.x 真实 state fixture 迁移回归测试
- `init()` 流程定稿;api-extractor report 作为公共 API 快照冻结
- theatric API 审查 + 测试 + 文档;成色不足则以 0.x 版本发布,不阻塞主线

出口标准:公共 API 冻结候选;迁移指南初稿。

### P3 协作最小闭环

- sync-server 自托管文档(docker-compose 已有)、env 配置简化
- 自托管场景下鉴权简化或可关闭
- studio 服务器连接设置入口;presence/冲突 UI(`uesConflicts`)收尾或隐藏;断线状态指示

出口标准:两个浏览器经自托管 sync-server 实时同步。

### P4 发布

- CHANGELOG 从 0.4.5 补齐到 1.0;0.7→1.0 迁移指南
- 发布脚本 / CI;compat-tests 适配新 scope;rc dogfood

出口标准:1.0.0 发布到新 scope。

## 回退触发器(管理决策点,非代码功能)

路线 A 的风险是 saaz 同步引擎的调试工期无界(确定性回放、时钟一致性、会话恢复竞态)。触发器把无界风险变为有界。

**触发条件(全部满足):**

1. P1 的实现类任务已全部完成(做完但不稳,而非没做完);
2. P1 三个出口标准在额外 2 个修复里程碑(约 4–6 个会话的集中调试)后仍不能全部达成。

**触发后的动作:暂停 P1,向用户报告现状与选项(切换方案 B / 继续调试 / 其他),由用户拍板。任何情况下不自动执行切换。**

若用户选择切换方案 B(Redux 回退):

- P1 重做:从 git 历史恢复 0.7.x Redux 版 StudioStore + localStorage 持久化
- saaz 保留在仓库,仅 serverUrl 模式使用
- P3 协作重新设计为 Redux→saaz 桥接,范围缩为实验性
- P2 / P4 基本不受影响(损失封在 P1 内)

## 数据流与 0.7 state 兼容

### 单人模式写入与恢复路径

```
编辑 → studio.transaction() → saaz.tx()
  ├─ 乐观应用到本地 atom(UI 立即响应,延迟与 0.7 相同)
  ├─ 事务入 optimisticUpdatesQueue + undo 栈
  └─ 发给后端(单人 = 进程内 SaazBack)
       ├─ 后端应用、clock+1
       └─ 持久化:back 侧 snapshot/clock/updates → BackIDBAdapter ┐
front 侧快照/会话状态 → FrontIDBAdapter ─────────────────────────┤→ IndexedDB
重新加载 → _init 从 IDB 恢复(快照 + 会话 + 未同步队列) → 离线完整可用
```

协作模式唯一变化:后端换成 tRPC 远程,presence 经 subscribe 推送,多 peer 时钟合并;front 代码不变。

### state 兼容分两层

**第 1 层:格式兼容(core 职责,风险低)。** 需要兼容的是项目状态(sheets/keyframes/objects,即 `createContentOfSaveFile` 的 JSON),不是 studio UI 布局。core 已有 state 版本迁移机制(`initialiseProjectState`);工作是把 0.7.x 代表性 fixture(关键帧、compound props、assets)做成回归测试,覆盖导入/导出链路。

**第 2 层:存储介质迁移(新增,风险中)。** 0.7 存 localStorage(key `theatrejs:0.4`),1.0 存 IndexedDB。一次性迁移器:

```
首次启动 → 检测 localStorage 存在 0.7 blob?
  ├─ 无 → 正常初始化(新用户)
  └─ 有 → 解析 → core state 校验/迁移 → 作为 saaz 初始快照写入 IDB
         → 原 localStorage 数据保留不动(只读不删)
```

**范围声明:只保证项目状态兼容;studio UI 布局状态(面板位置、选择集等)不迁移,升级后重置为默认。**

## 错误处理

核心原则:**单人模式下,任何持久化/迁移/网络错误都不能阻塞编辑本身**——编辑永远可用,其余皆可降级。

| 失败场景 | 处理 |
|---|---|
| IndexedDB 不可用(隐私模式/quota 满) | 降级 FrontMemoryAdapter,studio 内提示"本次状态不会被保存";不崩溃不阻塞 |
| 0.7 blob 迁移失败 | 旧数据保留在 localStorage,从头初始化,UI 提示可手动导出恢复(复用 StateConflictRow 雏形) |
| 协作模式断网/服务器不可达 | 利用 saaz 乐观更新 + 重连;P3 补 UI 离线指示,不静默失败 |
| 确定性回放失败(testDeterminism 抛出) | 开发环境 fail-loud;生产环境捕获降级,丢弃该事务并提示,不崩 studio |
| clearPersistentStorage 等待补方法 | 按 0.7.x 语义实现并配测试 |
